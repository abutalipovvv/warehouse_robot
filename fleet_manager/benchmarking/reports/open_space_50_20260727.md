# Open-space comparison: 50 robots

Date: 2026-07-27  
Seed: `20260727`  
Motion: `1.37 m/s`, rotation `0.9 rad/s`, Fleet Manager acceleration
`0.6 m/s²`  
Workload: one active distant order per robot, graph-distance window 30–160
steps, farthest 8% candidate pool, 5 minutes generation plus up to 3 minutes
drain.

## Starting conditions

- 50 unique random LMs.
- Minimum initial robot-centre distance: 2.4 m.
- Fleet Manager Sim and RDS used the same LM assignment.
- Both systems were run separately so they did not compete for CPU.
- All test orders were removed after the measurements.

## Fleet Manager Sim: full open map

Map: `benchmark_open_kiva`, 1188 LM.

- Generation window: 100 generated, 50 completed.
- Throughput: 10.01 orders/min.
- Average goal distance: 43.82 m.
- Average completed-order duration: 172.92 s.
- P95 duration: 239.68 s.
- First half: 4.8 orders/min; second half: 15.2 orders/min.
- Average/max waiting robots during generation: 14.31 / 23.
- Wait cycles at 300 s: 2 detected, 1 resolved.
- Runtime safety rollbacks: 0.
- After 180 s drain: 97/100 completed, 3 still waiting.

Conclusion: no time degradation over the five-minute generation phase. The
second half was faster than the first after the initial full-fleet wave had
warmed up. Three residual dependencies did not drain.

## Common RDS-visible subgraph

The current RDS import exposes only the first 360 ordered LMs:

- `B1036` (LM 360) accepts and executes an order.
- `B1101` (LM 361) returns RDS error 60001: point does not exist.
- Points farther down the map return the same error.

A matching `benchmark_open_kiva_rds360` bundle was therefore loaded into Fleet
Manager Sim for a like-for-like topology test.

Fleet Manager Sim result on 360 LM:

- Generation window: 101 generated, 51 completed.
- Throughput: 10.23 orders/min.
- Average goal distance: 35.22 m.
- Average completed-order duration: 150.25 s.
- P95 duration: 239.10 s.
- First half: 8.0 orders/min; second half: 12.4 orders/min.
- Average/max waiting robots during generation: 27.75 / 50.
- Wait cycles: 18 detected, 17 resolved.
- Runtime safety rollbacks: 0.
- After drain: 78/101 completed, 23 still active.

The dense 10x36 topology produced a brief 50/50 global stall near 290 s. The
fleet recovered without rollback, but drain performance remained weak.

## RDS Core

A valid 50-robot throughput measurement could not be obtained with the current
RDS instance:

1. On the full 1188-LM workload, goals outside the first 360 LMs failed with
   RDS error 60001 (`doesn't has point`). The first invalid run produced 100
   failed orders in 32.6 seconds and was discarded.
2. Restricting every start and goal to the valid 360-LM subgraph removed those
   missing-point errors.
3. A burst of `setOrder` calls caused port 8088 to disappear and RDS to
   auto-recover.
4. Pacing at 5 orders/s still caused a restart around the 11th order.
5. Pacing at 1 order/s still caused a restart around the 19th order.

Single-robot controls worked:

- `B0419 -> B0420`: completed in about 2 s.
- Ten horizontal graph steps: completed in about 10 s.
- Six vertical graph steps: completed in about 10 s.

Therefore the map geometry and individual navigation are functional; the
blocking issue is RDS map/import capacity and multi-order stability, not
single-robot motion.

## Comparison

Fleet Manager Sim demonstrably accepts and controls all 50 simultaneous
orders. It maintains roughly 10 orders/min on both the full map and the dense
common subgraph without collision rollback. Its remaining weakness is
long-tail waiting: coupled conflict repair did not clear every order during
the drain window.

The current RDS installation executes individual routes quickly, but cannot
currently enter a valid 50-order steady state. It is therefore not possible
to claim that either traffic algorithm has higher throughput until the RDS
360-LM import boundary and restart under 11–19 concurrent submissions are
fixed.
